## 1. LLM执行摘要

- 当前任务的直接目标是回答“为了让意图类拼图与实现类拼图严丝合缝，当前架构还缺什么、下一步需要补什么”。
- 首要工作对象不是具体业务代码，而是围绕目标元素 1272 的架构缺口、目标架构、验证闭环与反馈回路。
- 优先检查 `Core Architecture Gap`、`System Requirement`、`Target Core Architecture`、`System Architecture Description` 之间是否已形成可执行的闭环。
- 同时检查“意图 -> 实现 -> 测试验证 -> 问题反馈/架构反馈”链路是否已经在 KG 中明确落地到 1168、1177、1178、1179、1180、1181。
- 若要补齐治理能力，再评估 `AI4PB VS插件`、`Prompt Tool Registry`、`ai4pb-task-support` 是否需要承载新增的追踪字段或执行步骤。
- 不允许跳过架构层分析直接扩散为大范围代码改造。
- 最关键验收条件是：输出的缺口与补齐动作必须能逐条追溯到具体架构元素 ID 或明确标注为假设。
- 当前最大风险是 1272 在 KG 中缺少与下游架构对象的显式关系，容易把合理推断误写成已确认事实。
- 当前任务没有 `ResolverNotes`，历史处理线索不足，需先形成“已确认事实 / 未知项 / 补齐建议”三分结构。

## 4. 约束与边界

- 必须遵守 `Progressive Disclosure`：先把目标拆成缺口、需求、目标架构、实现、验证、反馈几个可核对节点，再逐步补齐，禁止一次性给出无追踪的大而全方案。
- 必须遵守 `Separation of Concerns`：战略目标、架构描述、实现系统、验证机制、问题反馈必须分层表达，禁止把架构补齐、代码实现、流程治理混为一个笼统结论。
- 必须遵守元素 1161 的建模约束：下层建模不能引用上层元素；如需表达跨层影响，应通过合适的架构关系与层次分解处理。
- 在未确认必要性前，必须保持 `AI4PB VS插件`（1209）、`Prompt Tool Registry`（1219）、`ai4pb-task-support`（1211）的现有职责边界不变。
- 明确禁止把视图 151 中“同图出现”误写成“已存在关系”。当前视图只证明 1246 与 1272 同时被纳入该视图，不证明两者已建模出语义连接。
- 明确禁止凭空补写任务特定原则、约束、接口或实施结果；无法确认时只能写 `未知` 或 `需人工确认`。
- 若需新增验收规则、追踪对象或治理节点，但 KG 中没有可复用对象，必须显式标注 `需新增架构元素`，不能伪装成既有元素能力。

## 9. 风险、阻塞与缓解措施

- 风险：目标元素 1272 与下游元素缺少显式关系，容易造成过度推断。
  - 缓解措施：所有跨元素结论必须标注“已确认”或“需人工确认”，并优先建议补关系而非补叙述。
- 风险：缺少任务级原则、约束与验收量化标准，导致“缺什么”“做什么”口径不一致。
  - 缓解措施：显式提出 `需新增架构元素`，把原则、约束、验收指标结构化补齐。
- 风险：可能把本任务误解为代码改造任务，直接进入实现层修改。
  - 缓解措施：先完成架构缺口分析和影响评估，只有确认影响执行链路后才进入代码层。
- 风险：任务没有历史处理记录，无法知道此前尝试过哪些方案。
  - 缓解措施：本轮先输出首版差距矩阵，后续通过 `ResolverNotes` 逐轮累积。
